# DS220j: DSM 7.4 and RTL8156B

This fork investigates a Synology DS220j (RTD1296), DSM 7.4.1-90080,
and an RTL8156B USB 3.x 2.5 GbE adapter. These are the target configuration,
not a claim of successful hardware validation.

## Known limitation

Upstream [issue #275](https://github.com/bb-qq/r8152/issues/275) tracks
RTD1296 stalls, particularly while transmitting from the NAS. A 2500 Mb/s
link, a successful package install, or a short benchmark does not establish
reliability. The exact adapter revision must be checked from device information
and driver logs; do not infer it solely from the retail label.

The DS220j has rear USB ports only. Try each directly with the same cable.
Use MTU 1500 initially. Keep the built-in 1 GbE interface connected for management.
Use a distinct IP address for the USB interface and explicitly target that address
during tests. Do not configure both interfaces with the same IP address.
A 2.5 GbE switch/client or a correctly configured direct connection is needed.

## Package selection and upgrades

For the stated configuration, use the upstream RTD1296 package with the
`_7.4.spk` suffix (release 2.22.1-1 includes it):
[r8152-rtd1296-2.22.1-1_7.4.spk](https://github.com/bb-qq/r8152/releases/download/2.22.1-1/r8152-rtd1296-2.22.1-1_7.4.spk).

That upstream binary does NOT contain changes proposed in this fork.
Fork source changes require a matching Synology SDK/toolchain build and testing.
Do not force-load an incompatible module or edit package metadata to bypass checks.

Before updating DSM, verify a compatible driver package is available, retain a
copy of the current package, and confirm management access through built-in LAN.
After updating, install the compatible package and distinguish these failure cases:

- Missing `/opt/sbin/spk_su` or permission setup: follow the upstream DSM 7
  installation instructions below. DSM updates can remove the helper.
- Kernel `version magic` / `invalid module format` errors: install/rebuild the
  module for the running DSM kernel. Recreating a privilege helper cannot fix an ABI mismatch.
- Driver loaded and link up, but transfers stall: investigate issue #275 rather
  than repeatedly reinstalling the package.

For the documented DSM 7 helper setup, after the package files have been installed:

```sh
sudo install -m 4755 -o root -D /var/packages/r8152/target/r8152/spk_su /opt/sbin/spk_su
sudo chmod a+rx /opt /opt/sbin
```

Retry installation or start the package in Package Center as appropriate.
These privileged steps are needed when setup is missing, not after every upgrade.
Verify the module loads and the USB interface has its intended IP address.

## Validation plan

1. Record DSM build, kernel, package version, USB adapter revision, port, cable,
   switch/client, MTU and enabled offloads before changing anything.
2. Confirm the adapter enumerates at USB SuperSpeed (5000 Mb/s or above), and
   Ethernet negotiates 2500 Mb/s. USB 2.0 fallback cannot meet this goal.
3. With an independently installed native `iperf3` server on the NAS, run the
   following from a 2.5 GbE client. Replace USB_NAS_IP with the USB interface IP:

   ```sh
   iperf3 -c USB_NAS_IP -t 300
   iperf3 -c USB_NAS_IP -t 300 -R
   ```

   The first test receives on the NAS; `-R` sends from the NAS, the reported
   problem direction. Capture both endpoints' output and errors. A sender-only
   UDP rate is not proof of delivered throughput.
4. Copy a large disposable test file in both directions over SMB and compare its
   checksum. Exercise repeated small-file access too. Record CPU load and stalls.
5. Repeat after an idle period and a normal reboot. A five-minute pass is a
   screening test, not proof of long-term reliability.
6. Change one setting at a time and repeat the identical workload. Preserve
   baseline results. If throughput falls below built-in Ethernet, record that as
   a regression even when the displayed link remains 2500 Mb/s.

No reliable RTD1296 fix or throughput guarantee is claimed here. Disabling EEE,
ordinary network offloads, or using a newer adapter has not consistently solved
the upstream reports. A powered USB 3 hub can isolate a power issue but is not a
proven fix. Forcing 1 Gb/s or USB 2.0 defeats the 2.5 Gb/s objective.
